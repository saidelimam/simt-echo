## 1. Bundle crypto (ECX1) — APPROVE

- Container `C = "ECHO" ‖ 0x01 ‖ SHA-256(body) ‖ body`, sealed file
  `E = "ECX1" ‖ AES-256-GCM(key, C)`:
  `shared/src/commonMain/kotlin/app/simt/echo/bundle/BundleCodec.kt:25-42`.
- Fresh AES-256 key per offer (`keyGenerator(AES.Key.Size.B256).generateKey()`
  inside `seal`, `BundleCodec.kt:53-58`); the platform crypto provider does
  the generation, not app code.
- Open is fail-closed on a closed error set (`BAD_MAGIC, NEEDS_KEY,
  DECRYPT_FAILED, HASH_MISMATCH, UNSUPPORTED_VERSION, EXPIRED`,
  `BundleCodec.kt:13-20`): encrypted bundle without key refuses
  (`BundleCodec.kt:66-70`); wrong key refuses (`BundleCodec.kt:85-97`);
  hash is verified over received bytes before decode (`BundleCodec.kt:99-122`).
- QR carries the AES key (`k=`) plus a 16-byte LAN token (`t=`) and an
  8-byte body fingerprint (`s=`):
  `shared/src/commonMain/kotlin/app/simt/echo/transfer/QrPayload.kt:6-21`.
  Receiver re-opens with the QR key and rejects on fingerprint mismatch
  (`TransferService.kt:98-106`). The key-in-QR is the pairing trust model
  (optical channel), not a leak — recorded as residual R2.
- QR parsing is strict: IPv4-only host, port range, exact token/key sizes,
  lowercase-hex fingerprint, version gate (`QrPayload.kt:64-105`); covered
  by `QrPayloadTest` (round-trip, 200-char scanner limit, rejection cases).

## 2. Relay zero-knowledge — APPROVE (with residual R4)

- Server stores one sealed bundle per 6-char code for 30 min and never
  receives the key — key travels in QR `k=`, code in `c=`
  (`worker/src/relay.ts:1-12`, `postRelay` at `relay.ts:58-79`,
  expiry delete-then-404 at `relay.ts:91-96`).
- Client uploads/downloads sealed `ECX1` bytes only; key never leaves the
  QR path (`RelayClient.kt:14-20`, `KtorRelayClient` at `RelayClient.kt:40-65`).
- Wiring uses the same production config as the API client, null until
  configured so Share stays LAN-only (`AppGraph.kt:98-107`,
  `TransferService.kt:44`); LAN-first/relay-second with no masking of
  corrupt bundles (`TransferService.kt:108-124`).
- Live round-trip on production recorded in `docs/release.md:135-150`
  (POST random ECX1 blob → code → byte-identical GET; server sees opaque
  bytes). TTL expiry is code-cited, not live-awaited — residual R4, owned
  by W9-04's device pass.

## 5. Expiry purge on both phones — APPROVE (with residual R3)

- Sender side: startup purge (`EchoApplication.kt:26-33`) backed by
  `RouteRepository.purgeExpired` (`RouteRepository.kt:86-100`); share/export
  paths refuse expired routes fail-closed (§4).
- Receiver side: `fetchPreview` enforces expiry at open with the receiver's
  clock (`TransferService.kt:98-106` → `BundleCodec.kt:76-81`); an expired
  bundle can never be saved via `receive`.
- Purge runs at process start on every phone, so both ends converge without
  any server round-trip. Gap: a long-running process holds expired routes
  until restart — residual R3 (export paths stay fail-closed regardless).

## 8. Residual risks (none blocking)

- **R1 — LAN token RNG is not a CSPRNG.** `randomBytes` defaults to
  `Random.nextBytes` (`TransferService.kt:37,67`). Bounded: the token is a
  LAN bearer only; the bundle still needs the QR key (platform-crypto
  random) to decrypt. Recommend `SecureRandom` before store submission;
  one-line hardening, not a release blocker.
- **R2 — QR key is cleartext by design.** Any party that photographs the
  QR gets the bundle key. This is the pairing trust model; exposure window
  is bounded by export expiry + startup purge (§5). Note in W9-12
  limitations; no change.
- **R3 — Purge runs at process start only** (`EchoApplication.kt:26-33`).
  A long-running app keeps an expired route visible until restart, though
  it can never be shared or exported (§4–§5). Consider purge-on-resume
  post-v1.
- **R4 — Relay TTL + LAN-blocked transfer not yet device-proven.**
  Inherited from `docs/release.md:145-150`; owned by W9-04. Unit + live
  round-trip evidence stands.
- **R5 — No second-phone relay E2E in this audit.** Same owner (W9-04).
- **L1 — Token-value limitation** as in §7 (method constraint, not a risk).

No BLOCK findings → no slices re-opened; nothing stands between this audit
and W9-12 except the already-queued W9-04…W9-07 device evidence.
